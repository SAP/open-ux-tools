# Data and heuristics: design record

This record explains where the generator's domain knowledge lives, how it is protected, and what its limits are. Paths are relative to `packages/mock-data-generator`.

## 1. Classification of data that used to live in code

Every table, vocabulary and list that the generator once embedded in TypeScript was put in one of three classes.

| Class             | Rule                                                                                                            | Where it lives now                                                                                                                                                                                                                                                                                                                                                                      |
| ----------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Delete**        | Rules fitted to individual test fixtures, which encode no general knowledge                                     | Removed. Behaviour that mattered is covered by general rules and by tests.                                                                                                                                                                                                                                                                                                              |
| **Externalize**   | Domain data a maintainer may extend without changing code: vocabularies, value banks, role definitions, prompts | Versioned JSON resources, each pinned by SHA-256 in `resources/models/manifest.json` (see section 5): `resources/rules/semantic-rules.v1.json` (schema `resources/rules/semantic-rules.schema.json`), `resources/rules/role-registry.v1.json`, `resources/banks/value-banks.v2.json`, and the SFT prompt texts under `promptTemplate` in `resources/models/sft/generation-config.json`. |
| **Keep and cite** | Values fixed by a published specification, product limits, and declarations that describe code                  | Specification constants in `src/spec/*.ts`, each block citing its source; tunable limits in `src/limits.ts`, each named once with its reason; two code declarations exempted by the guard test (section 6).                                                                                                                                                                             |

Each resource has a strict parser that rejects unknown keys, wrong types and duplicates, so a defective resource stops the package from loading instead of being partly ignored:

| Resource                                      | Parser                                                             | Content                                                                                                                                                                             |
| --------------------------------------------- | ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `resources/rules/semantic-rules.v1.json`      | `parseSemanticRuleStore` in `src/semantics/rule-store.ts`          | SAP abbreviations, lexical rules, ABAP Dictionary data elements, metadata roles, temporal and coherence vocabulary, VDM field groups, model output filters, role policy, thresholds |
| `resources/rules/role-registry.v1.json`       | `parseRoleRegistry` in `src/semantics/role-registry.ts`            | Semantic role definitions: compatible primitive types, key policy, validator, key domain                                                                                            |
| `resources/banks/value-banks.v2.json`         | `parseValueBankStore` in `src/semantics/bank-store.ts`             | Role and concept value banks, code/text pairs, record banks (locations, units, ISO 4217 currencies), numeric ranges                                                                 |
| `resources/models/sft/generation-config.json` | `parseSftConfiguration` / `parseSftPromptTemplate` in `src/model/` | Model shape, sampling options, system prompt, example row, ChatML markers                                                                                                           |

The value order inside the resources is part of the contract: seeded generation draws by index, so reordering values changes output for the same seed.

The execution modes `api`, `data-editor` and `start-mock` of `createMockDataGenerator` are budget presets named by the host's purpose. `api` and `start-mock` apply no preset; `data-editor` applies the `DATA_EDITOR_SFT_*` limits. Explicit generation options always win. Within the SFT service budget, each entity set the model fills may use what remains of the budget, up to the per-entity timeout, and returns as soon as its fields are done; the entity sets of `sftPriorityTargets` go first. An even share would leave a wide entity set too little time to finish a single call on a small machine. `sftFieldsPerCall` sets how many fields one call writes; fewer fields per call finish sooner, so more of the model's values fit within the budget.

## 3. Heuristics and their limits

Field routing decides, per field, a metadata role first (an explicit annotation), then excludes technical and code-list companion fields, then arbitrates between the classifier and the lexical fallback (`src/semantics/lexical-fallback.ts`). All heuristics below read `resources/rules/semantic-rules.v1.json`.

| Heuristic                     | Rule store key        | What it does                                                                                                                                                                                                                                                           |
| ----------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Metadata roles                | `metadataRoles`       | Roles an explicit marker decides: an OData V4 vocabulary term matched by its lower-case qualified-name suffix (first match wins), or an OData V2 `sap:semantics` value.                                                                                                |
| ABAP Dictionary data elements | `dataElements`        | Maps upper-case data element names (for example `BANKS`) to roles when the metadata names the data element.                                                                                                                                                            |
| Lexical rules                 | `lexicalRules`        | Word rules over the field's name, label and description: a rule applies when the type is one it names, every `all` group and one `any` word are present (or the `lastWord` matches), and none of its `none` words occur.                                               |
| SAP abbreviation glossary     | `sapAbbreviations`    | SAP CDS element-name abbreviations and their full words. Only entries with `appliedInLexicalRules: true` are expanded before the lexical rules run; the others are listed for reference and expand nothing.                                                            |
| Role policy                   | `rolePolicy`          | Runtime routing policy kept apart from the fingerprinted role registry: roles that are authoritative, roles the lexical fallback may not assign, roles drawn from application domains, and permitted role refinements.                                                 |
| Thresholds                    | `thresholds`          | Uncalibrated fallbacks for route, conflict, lexical confidence and coverage statistics. A calibrated classifier head carries per-role thresholds that take precedence.                                                                                                 |
| Temporal vocabulary           | `temporalVocabulary`  | Words marking administrative timestamps (created, changed), interval bounds (start, end), used by the temporal plan to order dates within a row; clock words (an event's date, time and timestamp name one event).                                                     |
| Temporal spread               | `temporalSpread`      | Generation parameters for how far the later event of an ordered pair lies after the earlier one: the share of rows kept at one instant, the mean and longest gap in days, the range of minutes.                                                                        |
| Coherence vocabulary          | `coherenceVocabulary` | Name tokens of the generic coherence rules: phone and country, status and status text, field control, balance, currency and amount. Tokens are compared after splitting camel case, underscores and hyphens, in lower case.                                            |
| VDM field groups              | `vdmFieldGroups`      | Field-name profiles of SAP S/4HANA interface views (unit of measure, SI unit conversion, lifecycle, processing status). Names are normalized to lower case without separators; a profile applies only when a scenario opts into its coherence rule.                    |
| Model output filters          | `modelOutputFilters`  | Regular expressions that reject values the SFT model proposes: echoed instructions, placeholders, paths or URLs, and values that repeat the field's own name or ordinal.                                                                                               |
| Code texts                    | `codeTexts`           | Text suffix words that make a field the text or name of a code, the roles that yield codes and the roles that name them, the record source that names each code role (ICU regions, currencies, languages, or the units bank), and the shortest text kept.              |
| Geography                     | `geography`           | The anchor role of a row's place fields (country), the leaf roles of the record itself that follow it (city, region, postal code, telephone numbers, time zone), and the roles of another party (bank and BIC) that follow only a country field sharing their context. |
| Typed floor                   | `typedFloor`          | The longest string the typed floor treats as a short code and the range of code ordinals it writes.                                                                                                                                                                    |
| Realism guard                 | `realismGuard`        | How many words of a service name, or how many counted numbers in a column, make a generated value a placeholder.                                                                                                                                                       |
| Realism checks                | `realismChecks`       | Vocabulary and thresholds of the realism checks in `src/quality`, kept apart from the generator's own vocabularies: form, country, time and event words, and the shares and row counts from which a pattern counts.                                                    |
| Organisation name evidence    | `rolePolicy`          | `organizationNameEvidence`: the subject and display words by which the lexical fallback routes a field to the organisation name; the word before the display word is the head of the name.                                                                             |

### Documented limits

- **English-only tokenization.** Vocabularies, abbreviations and lexical rules are English words. Model output filters lower-case values with the `en-US` locale. Names, labels and descriptions in other languages produce no lexical match and fall to the classifier or the deterministic structural providers.
- **ASCII identifiers.** `src/naming.ts` splits identifiers at camel case, underscores, hyphens and whitespace, and only ASCII letters and digits take part in case boundaries. Identifiers in other scripts are kept whole (one token per delimited run), never translated. The temporal planner keeps only ASCII letters of each token.
- **SAP naming conventions.** The rules assume SAP and CAP naming: Pascal or camel case, `_` separators (as in `to_Booking`, `BookingStatus_code`), SAP CDS abbreviations, upper-case ABAP Dictionary data elements and the `SAP__` prefix for Gateway protocol sets. Services that follow other conventions get fewer lexical routes.
- **Abbreviations applied vs listed.** Only abbreviations marked `appliedInLexicalRules` are expanded. Listing an abbreviation does not make the lexical rules understand it; a lexical rule that names an expanded abbreviation instead of its full word is rejected by the parser as unreachable.
- **The typed floor abstains rather than invents.** A string field that no role, enumeration, value list or model can fill keeps the code shape when its metadata declares a text, a value list or a value help for it (`Common.Text`, `sap:text`, `Common.ValueList*`, `sap:value-list`); a name form (a name ending in a text word, such as `RegionCodeDesc`) never does. Any other such field is left empty (null when nullable, else the empty string), whatever its length: a short column may hold a flag, a word or a code. It is never filled with a label and a row number (`Unit Price 1`), which looks like data and is not; the standard mock server fallback below fills it last. The result counts these cells in `abstentions.typedFloor`.
- **Realism guard.** After finalization, a generated string that is a field or entity name of the service, a service name of at least `realismGuard.minimumEchoedWords` words followed by a number, or a service name its column counts up (at least `realismGuard.minimumCountedNumbers` different numbers), and, in a field named as a text (`realismChecks.textFieldWords`) that is no code's text, the codes of a column that codes fill (`realismChecks.codeShare`, the code-text check's own criterion) are withheld the same way, whatever tier wrote it, and reported once per field as `REALISM_VALUE_WITHHELD` and in `abstentions.realismGuard`. Supplied rows, keys, enumerations, relationship ends and unit or currency fields are never changed. A withheld value whose absence the field's planned role rejects, or that takes a row out of its value-list tuple, is put back (`src/generation/final-checks.ts`), so the guard never aborts a generation. The guard shares its tests with the realism checks in `src/quality/`; a single word followed by a number (`Room 14`), and a counted value that is no name of the service (`Floor 1`, `Floor 2`, `Floor 3`), are not treated as placeholders.
- **Value-list keys.** A key whose value list (`Common.ValueList`, `sap:value-list`) maps it to the single key of an entity set of the service takes that key's values, as a key a relationship maps to a key does: projection never rewrites keys, so without the link a key could name a value-help row that does not exist, and its text would stay empty.
- **Rows rejoin their value-list tuples before the last steps.** Format providers, coherence and code texts run after value-list projection and may rewrite a field a value list determines. A generated row that is then no member of a tuple it could still adopt (one whose values fit the owner's facets and planned roles and agree with its protected fields) adopts one, chosen together with every list that shares a field with it, so each shared field receives one value (`adoptCompatibleTuples` in `src/generation/tuple-domain.ts`). Rows without such a tuple keep their values and are reported as `SEMANTIC_DOMAIN_CONFLICT`.
- **A near value beats no value.** Wherever a step would give up on a field, it takes the closest value it has. A field the classifier was not certain about (below its route threshold or between two roles), or whose role its form, facets or domain withdrew, takes the best-ranked classifier role that fits it and passes the same plan review, as long as the classifier ranks that role above `unknown` and with at least the rule store's `thresholds.bestEffort` confidence (`adoptBestEffortRole` in `src/generation/semantic-plan.ts`). That threshold is calibrated on held-out labelled fields: it is the lowest confidence at which at least 80% of such roles belong to the family of the field's labelled role, so a weaker guess keeps the standard fallback rather than a likely wrong value. A role another field of the entity holds is skipped. Keys, technical fields and fields the classifier calls unknown take none. The decision is marked `bestEffort` and reported as `SEMANTIC_ROLE_BEST_EFFORT`; its values fill the field and the model tier may still replace them with values the role accepts, since it keeps the classifier's confidence.
- **Model values are kept when the relevance check cannot confirm them.** The relevance check reads model captions of linked texts and of generated code/text domains, but a caption that passes the field's constraints (letters, its facets, different from its code, no echo or placeholder) is kept whatever the check says, and an unconfirmed one is reported as `SFT_CANDIDATE_RELEVANCE_UNVERIFIED` (`src/generation/sft.ts`). A generated code/text domain needs one usable row: a row that repeats a code or fails a field is dropped and the others are kept, so a status list the model gives three codes for has three rows. A code the model shows with different captions in different rows keeps the caption of its first row, so the text stays a function of its code.
- **Standard mock server fallback, last.** After every tier, the realism guard and the coherence rules, a generated string cell that is still empty (null or the empty string) gets the value the standard SAP Fiori elements mock server (`@sap-ux/fe-mockserver-core`) writes for a string it has no data for: the property name, an underscore and the zero-based row index (`BankNumber_3`), when the whole name fits the declared maximum length (`src/spec/standard-mockserver.ts`, `src/generation/standard-fallback.ts`). A column too short for the whole name holds a code of the name's initials instead (`BNK07`, or one letter or digit), since a cut-off name (`Addr_0`) means nothing. An indicator (a role of the boolean family) and a field a configured coherence rule decides keep their empty value, which there means "no". The value says plainly that nothing knew what the field holds, which a label and a row number (`Bank Number 3`) does not. The relations of the service are kept: the text of a code takes the index of the first row with that code, so each code keeps one text; an owner field a value list determines is copied from the matching value-help row rather than invented; an owner field several value lists determine, and the value-help columns it reads, are left as they are, since the lists may disagree; keys, enumerations, relationship ends and supplied rows are never changed. A value the field's planned role rejects is not written, so a URL, phone, BIC or currency field that no tier filled stays empty rather than hold a name and a number. Whatever still makes a final semantic or value-list check fail that passed before the fallback is undone for the entity sets involved (`src/generation/final-checks.ts`), so the fallback never aborts a generation. The result counts these cells in `abstentions.standardFallback`, and the realism checks do not count them as placeholders, name leaks or shared texts; the realism judge sees them as empty. The test is the value's shape, so a model value of exactly that shape (`BankNumber_12`) is treated the same way.
- **Descriptive key columns.** A view often keys every column. When a key has an integer or UUID column that no relationship, enumeration or draft protocol fixes, that column alone tells the rows apart, so the key's decimal, boolean, date and time columns get no allocated ordinal and take the values their meaning gives them, like non-key fields. Its name-form strings (`codeTexts.textSuffixes`) keep the allocated value as a floor, since a key cell is never left empty, and the model tier may replace it (`src/generation/key-identity.ts`). The realism guard does not withhold key cells, so a model value in such a column is only checked by the hard realism checks and the judge. Without such a column every key column keeps its allocated value.
- **Every result is checked.** The hard realism checks (placeholder, name leak, code text, temporal order; `REALISM_HARD_CHECKS` in `src/quality/realism-types.ts`) run over the generated rows of every result, supplied rows skipped, and the result reports the checks' version, how many generated fields fail one and whether none does (`realism`). The placeholder and name-leak checks re-test what the guard withheld, so a drift between the two shows up here. `MockDataGeneratorInfo.realismReady` stays a package capability flag, true in API version 2, which API version 2 hosts require.
- **Free texts come from the host or a model, never from a packaged list.** What a description, note, comment or remark says depends on the service's domain, which the generator cannot know. The value banks write one only from the descriptions of a sample set the host supplies (`sampleDataset`); with the packaged sample set they abstain. Any field no deterministic tier gave a value in any row, routed or not, is offered to the model tier, which writes it from the field's name, label and entity.
- **Domain names come from the host too.** Which products, equipment, sources or accounts a service names depends on its domain as much as its free texts do: `product_name`, `equipment_name`, `source_name` and `account_description` are written only from the role samples a host supplies (`sampleDataset.roleSamples`); otherwise the field is left to the model tier or empty.
- **Unbounded ranges are documented parameters.** Where no metadata bounds a value (how many days an end date lies after its start, a house number, a page number, a count in a string field, decimal places, the power of ten of a unit dimension), it is drawn from an inclusive range in `generationRanges` of the rule store, whose notes state that these are generation parameters, not facts. Facets still apply.
- **A value is written whole or not at all.** A bank value longer than the field's `MaxLength` is not cut to fit: a cut code is another code (`ES` cut to one letter is `E`, the SAP language key of English) and a cut name is no name. The field takes another bank value that fits, or is left to the next tier.
- **A status bank names only its own codes.** When the metadata declares no status codes, a status code and its text come in pairs from the status bank. A code the metadata declared, or another source fixed, gets the words it spells (`IN_PROCESS` gives `In Process`) or the code itself, never the bank's meaning of the same letter (`A` is not assumed to mean approved) and never a label-and-number text (`Status 0`).
- **Texts of codes are functions of their codes.** The text of a code is the field its `Common.Text` or `sap:text` annotation names, or a string sibling named as the code followed by a text word (`PaymentGroup`, `PaymentGroupText`). Such a text never keeps a narrative role (description, notes, remark and the like), unless the code is a number or the entity's own key outside a value list, where the text describes the row; neither a text of a code nor a name form keeps a role that yields codes; it takes the role naming them instead (`country` becomes `country_name`), so a one-word text sibling (`Currencyname` of `Currency`) holds names, not codes. Across the service, every row of a code carries one text, taken in order from supplied rows and cells another entity fixed, the name a record bank or the host's ICU data gives the code (country, currency, language, unit), or the first text generated for the code; nothing is invented for a code none of them names, which keeps what it holds (empty unless a tier wrote a value that is no text). Only a text that a record, a supplied row or a fixed cell names counts in the recognised tier. The domain of a code is the value list it belongs to, or else every code field of the same name.
- **Place fields follow the row's country.** The location bank holds one record per country (city, region, postal code, telephone numbering, a major bank with its head-office BIC, IANA time zone). After references and value lists have supplied the final country of each row, every generated place field of the record (the `geography` leaf roles) is drawn from the location record of that country; a time zone longer than its field is left empty. A bank and its BIC belong to another party: they follow a country field only when it shares a context word with them or their entity (`BankCountry`), and otherwise name one bank together; a free country follows a city or BIC another entity fixed. An entity with several country fields anchors each place field on the country field sharing the most name words with it. Place fields of a country the bank does not know are left empty rather than naming another country. A place field in an entity without a country field keeps the location of its row.
- **One timeline per row.** A row's start instant has a time of day drawn uniformly over the day, and the `time` role takes that time. Where generation wrote both events of an ordered pair (created/changed, start/end) at one instant, the later one moves later by the `temporalSpread` parameters. A pair is found by its words, or by its words without clock words when that alone matches (`creationTime` and `modifiedAt`); a generic label that names no event ("Time Stamp") gives way to the name. A date or time field naming the same event as the entity's one timestamp takes that timestamp's date or time. A record that belongs to a parent by metadata (its key includes the parent's key, or the parent contains it through an OData `ContainsTarget` navigation) is created no earlier than the parent: its creation and the events the plan orders after it move, its other dates stay, and a `SYNTHETIC_TEMPORAL_ASSUMPTION` diagnostic reports it. A plain reference says nothing about which record came first and orders nothing.
- **Heuristics never override explicit evidence.** Authored data, enumerations, value helps, explicit relationships and metadata roles take precedence over lexical and learned routes.

## 4. Determinism guarantees

| Tier                                                        | Guarantee                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Deterministic (`mode: 'deterministic'`, and every fallback) | Output depends only on the metadata, the request (targets and supplied rows), the seed, the options and the shipped resources. It is independent of the host locale: every order that reaches output, fingerprints or files uses code-point order (`compareCodePoints` in `src/ordering.ts`), never locale collation. `test/unit/locale-independent-order.test.ts` asserts that EDMX entity sets and CSN entity sets and properties are ordered by code point.      |
| Classifier                                                  | Repeatable for a given model bundle and ONNX runtime: inference has no sampling, and its decisions feed the deterministic providers. Floating-point differences between CPUs could in principle move a score that lies exactly on a routing threshold; the deterministic mode does not run the classifier.                                                                                                                                                          |
| SFT (row generator)                                         | Not deterministic across machines or loads. It runs inside time budgets (`DEFAULT_SFT_SERVICE_BUDGET_MS`, `DEFAULT_SFT_ENTITY_TIMEOUT_MS`, an optional deadline), so how many rows the model completes depends on hardware and load; the remaining fields keep their deterministic values. Identical requests (same model fingerprint, prompt, grammar, sampling and seed) are answered from the answer cache, in memory or in the optional `answerCacheDirectory`. |

The result reports which tier produced each value (`tiers`, `routing`, `executionMode`) and a fingerprint of the request, so callers can tell a reproducible result from a budget-dependent one.

## 5. Integrity chain

```
resource bytes ──SHA-256──▶ manifest entry (datasets[] or components[].files[])
                                   │
             component fingerprint ┤ (SHA-256 over role, path and digest of its files)
                                   ▼
                        manifest revision (SHA-256 over bundleId, runtime, fingerprints, dataset digests)
                                   │
                                   ▼
                  verified at session creation and before the first model load
```

1. **At session creation** (`createMockDataGenerator` in `src/standalone.ts`) the manifest below the session's resource root is parsed strictly and every declared dataset file below that root is re-hashed and compared with it. The first session fixes the root the value-bank store, the semantic rule store and the role registry are read from (`src/resource-root.ts`), so their files are verified before they are parsed. Any mismatch raises `RESOURCE_INTEGRITY`.
2. **On first use** those three resources are read once, hashed in memory from the exact bytes that are parsed, and parsed strictly; the manifest must declare exactly the in-memory digests. Importing the package reads no resource file, which keeps the package usable as an ES module or CommonJS bundle with a relocated `resourceRoot`. A parse failure raises `RESOURCE_INTEGRITY`. A later session whose root holds other bytes for these resources is rejected with `CONFIGURATION_INVALID`: one process uses one set of them, because every module reads them as fixed data and the classifier head pins the registry's fingerprint.
3. **Before the first model load** every model file is checked for size and SHA-256 (`verifyPackagedModels` in `src/model/packaged-models.ts`), once per process and manifest revision; never in deterministic mode.
4. **Cross-pins.** The classifier head pins the canonical fingerprint of the role registry (`registryFingerprint`), the serializer fingerprint, and the digests of the encoder and vocabulary, so a head trained against other roles or another encoder is rejected. The routing policy and thresholds are kept outside the registry so that tuning them does not invalidate a packaged head.

`node scripts/build-model-manifest.mjs` regenerates all digests from disk and `--check` fails when the manifest is stale; `pnpm check:package` repeats the verification on the packed tarball. See [model supply](../model-supply.md).

## 6. Guard against embedded data

`test/unit/no-embedded-data.test.ts` parses every file under `src/` with the TypeScript compiler and fails when an array literal, `new Set([...])` or `new Map([...])` holds more string literals than `MAXIMUM_LITERALS`. `src/spec/` is exempt because its constants are cited specification values, and the two declarations in its `CODE_DECLARATIONS` list (section 2) are exempt as code. A test also checks that each exemption still names a real declaration, so a stale exemption cannot hide new data. New vocabularies therefore go into the versioned resources, where the manifest pins them.

## 7. Errors and diagnostics

| Kind             | Type                                                                                    | Contract                                                                                                                                                                                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
