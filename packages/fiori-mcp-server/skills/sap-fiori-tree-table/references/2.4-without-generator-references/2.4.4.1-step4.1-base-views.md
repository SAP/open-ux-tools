# Step 4.1: Base Views (Transactional Layer)

Create 2 base views. Requires Step 3 hierarchy definition activated.

**⚠️ CRITICAL**: Activate BOTH base views before proceeding to Step 4.2 (Behavior Definition).

---

## Root Base View (e.g., `ZR_TravelRequest`)

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Travel Request - Base View'
define root view entity ZR_TravelRequest
  provider contract transactional_query
  as select from ZI_TravelRequest
  composition [0..*] of ZR_TravelActivity as _TravelActivity
{
  key TravelRequestUUID,
      TravelRequestID,
      EmployeeName,
      // ... other fields
      CreatedBy,
      CreatedAt,
      LastChangedBy,
      LastChangedAt,
      LocalLastChangedAt,
      
      _TravelActivity
}
```

**Key points**:
- `provider contract transactional_query` - Marks as transactional/managed view
- `as select from ZI_TravelRequest` - Sources from interface view
- `composition [0..*]` - Parent-child relationship to child base view

---

## Child Base View (e.g., `ZR_TravelActivity`)

```abap
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Travel Activity - Base View'
define view entity ZR_TravelActivity
  as select from ZI_TravelActivity
  association to parent ZR_TravelRequest as _TravelRequest
    on $projection.TravelRequestUUID = _TravelRequest.TravelRequestUUID
  association [0..1] to ZR_TravelActivity as _ParentActivity
    on  $projection.TravelRequestUUID  = _ParentActivity.TravelRequestUUID
    and $projection.ParentActivityUUID = _ParentActivity.ActivityUUID
  association [0..*] to ZR_TravelActivity as _ChildActivity
    on  $projection.TravelRequestUUID = _ChildActivity.TravelRequestUUID
    and $projection.ActivityUUID      = _ChildActivity.ParentActivityUUID
{
  key ActivityUUID,
  key TravelRequestUUID,
      ActivityID,
      ActivityName,
      ParentActivityUUID,
      SiblingOrderNumber,
      Location,
      ActivityType,
      // ... other fields
      CreatedBy,
      CreatedAt,
      LastChangedBy,
      LastChangedAt,
      LocalLastChangedAt,
      
      _TravelRequest,
      _ParentActivity,
      _ChildActivity
}
```

**Key points**:
- `as select from ZI_TravelActivity` - Sources from interface view
- `association to parent` - Links to root base view
- Same three associations as interface view (directory, parent, children)
- All associations must be exposed in select list

---

## Three Critical Associations

The child base view MUST maintain the same three associations as the interface view:

1. **`_TravelRequest [to parent]`** - Directory association
   - Links child to root entity
   - Required for hierarchy filtering
   - Used in behavior definition

2. **`_ParentActivity [0..1]`** - Self-reference to parent (upward)
   - Enables hierarchy traversal upward
   - Used in hierarchy's `ascending association`
   - Used for link/unlink actions

3. **`_ChildActivity [0..*]`** - Self-reference to children (downward)
   - Enables hierarchy traversal downward
   - Used in behavior's `descending association`
   - Used for cascading delete

---

## Why Base Views Are Separate from Interface Views

**5-Layer Architecture**:
- **Interface views** (`ZI_*`) - Basic data access, simple associations
- **Base views** (`ZR_*`) - Add transactional behavior, prepared for managed BO

**Purpose**:
- Interface views provide stable data contracts
- Base views add business logic layer (prepared for behavior)
- Separation enables reusability and maintainability
