## Implementation Workflow

### Step 1: Modify Database Tables (Generated)

**CRITICAL**: The RAP generator creates a child table with only `uuid` as a key. You MUST modify it to add a composite key.

**Root Table** (e.g., `ZZORGANIZATION`): Already generated ✓  
**Child Table** (e.g., `ZZEMPLOYEE`): **Modify key structure and add hierarchy fields**

**Key fields to MODIFY** (make parent_uuid a key):
```abap
key client      : abap.clnt not null;
key uuid        : sysuuid_x16 not null;
key parent_uuid : sysuuid_x16 not null;  // CHANGE: Make this KEY (generator had it as non-key)
```

**Why composite key**: Hierarchy requires keys = `[client, child_entity_uuid, root_entity_uuid]`. Without it, you'll get a "Primary keys do not match" error.

**⚠️ IMPORTANT: Field Naming and Types**
- `parent_uuid`: FK to root/directory entity (can be UUID or business key depending on root entity's key type)
- `parent_entity_uuid`: Self-reference for hierarchy (can be UUID or business key - must match child entity's key type)
- **If root uses business ID** (e.g., `organization_id`): Use `parent_organization_id` instead of `parent_uuid`
- **If child uses business ID** (e.g., `employee_id`): Use `parent_employee_id` instead of `parent_entity_uuid`
- This guide uses UUID examples, but the same pattern applies with business keys

**Fields to ADD to child table**:
```abap
parent_entity_uuid   : sysuuid_x16;      // Self-reference to parent
sibling_order_number : abap.int4;        // Ordering within same level
created_by           : abp_creation_user;
created_at           : abp_creation_tstmpl;
last_changed_by      : abp_lastchange_user;
last_changed_at      : abp_lastchange_tstmpl;
local_last_changed_at: abp_locinst_lastchange_tstmpl;
```

**Draft Table** (e.g., `ZZEMPLOYEE_D`): **Modify key and add matching fields (lowercase)**
```abap
key mandt      : mandt not null;
key uuid       : sysuuid_x16 not null;
key parentuuid : sysuuid_x16 not null;  // CHANGE: Make this KEY (all lowercase)
// ... then add:
parententityuuid     : sysuuid_x16;      // All lowercase, no underscores
siblingordernumber   : abap.int4;
createdby            : abp_creation_user;
createdat            : abp_creation_tstmpl;
lastchangedby        : abp_lastchange_user;
lastchangedat        : abp_lastchange_tstmpl;
locallastchangedat   : abp_locinst_lastchange_tstmpl;
```

### Step 2: Modify Base Views (Generated `ZR_*` Views)

**Do NOT create separate interface views (`ZI_*`)**. Instead, enhance the existing base views.

**Child Base View** (e.g., `ZR_EMPLOYEE`): **Add three associations**

```abap
define view entity ZR_EMPLOYEE
  as select from ZZEMPLOYEE as Employee
  association to parent ZR_ORGANIZATION as _Organization 
    on $projection.ParentUUID = _Organization.UUID
  association [0..1] to ZR_EMPLOYEE as _ParentEmployee
    on  $projection.ParentUUID = _ParentEmployee.ParentUUID
    and $projection.ParentEmployeeUUID = _ParentEmployee.UUID
  association [0..*] to ZR_EMPLOYEE as _ChildEmployee
    on  $projection.ParentUUID = _ChildEmployee.ParentUUID
    and $projection.UUID = _ChildEmployee.ParentEmployeeUUID
{
  key uuid                 as UUID,
  key parent_uuid          as ParentUUID,  // KEY because table has composite key
      employee_id          as EmployeeID,
      employee_name        as EmployeeName,
      // ... other business fields
      parent_employee_uuid as ParentEmployeeUUID,
      sibling_order_number as SiblingOrderNumber,
      // ... admin fields with semantics
      _Organization,
      _ParentEmployee,
      _ChildEmployee
}
```

**Three Critical Associations**:
1. `_Organization [to parent]` - Directory (already exists, verify it's correct)
2. `_ParentEmployee [0..1]` - Self-reference to parent (ADD THIS)
3. `_ChildEmployee [0..*]` - Self-reference to children (ADD THIS)

### Step 3: Create Hierarchy Definition

**Hierarchy View** (e.g., `ZI_EMPLOYEE_HD`):

⚠️ **No "Create Hierarchy" tool in ADT/MCP** - must create Data Definition manually, then replace with hierarchy syntax.

**Workaround**:
1. Create a Data Definition object first (skeleton)
2. Replace content with `define hierarchy` syntax
3. Activate

```abap
define hierarchy ZI_EMPLOYEE_HD
  with parameters
    P_OrganizationUUID : sysuuid_x16
  as parent child hierarchy(
    source ZR_EMPLOYEE
    child to parent association _ParentEmployee
    directory _Organization filter by
      UUID = $parameters.P_OrganizationUUID
    start where
      ParentEmployeeUUID is initial
    siblings order by
      SiblingOrderNumber ascending
  )
{
  key UUID,
  key ParentUUID,
      ParentEmployeeUUID,
      SiblingOrderNumber
}
```

**Critical elements**:
- `with parameters` - accepts directory/root UUID to filter the hierarchy
- `child to parent association` - upward link to parent node (`_ParentEmployee`)
- `directory` - filters by root entity (isolates hierarchies); use multi-line format with `filter by` on a new line
- `start where` - identifies root nodes (where parent UUID is initial/empty); use multi-line format
- `siblings order by` - defines ordering within the same level (SiblingOrderNumber ascending); use multi-line format

**🛑 ACTIVATE** hierarchy definition before proceeding.

### Step 4: Update Behavior Definition

Modify existing generated behavior definition to add hierarchy support.

**Add to Child Behavior** (e.g., in `zr_organization.bdef.abdl`):

```abap
define behavior for ZR_EMPLOYEE alias Employee
// ... existing configuration ...
{
  // ... existing fields and actions ...
  
  // ADD: Hierarchy parent-child link actions
  association _ParentEmployee
  {
    with draft;
    link action linkParentEmployee;
    unlink action unlinkParentEmployee;
  }
  association _ChildEmployee { with draft; }

  // ADD: Instance hierarchy configuration
  instance hierarchy ZI_EMPLOYEE_HD
  {
    managed reorder action changeNextSibling;
    field ( hierarchy-index ) SiblingOrderNumber;
    ascending association _ParentEmployee;
    descending association _ChildEmployee { with cascading delete; };
  }
  
  // ... existing mapping ...
}
```

**Critical additions**:
- **Link/unlink actions**: Enable drag-and-drop parent assignment
- **Hierarchy block**: Configures reordering, associations, cascading delete
- **Field marker**: `hierarchy-index` on SiblingOrderNumber

**Annotation Purpose**:
- `#LINEITEM_REFERENCE` facet - Displays the tree table in the root Object Page
- `presentationVariant` - Default sort by SiblingOrderNumber for proper tree rendering

  - **Child entity**: UUID (or business key), ParentUUID (or parent business key), ParentEmployeeUUID (or parent business key for self-reference), CreatedBy, CreatedAt, LastChangedBy, LastChangedAt, LocalLastChangedAt
  - **Note**: Field names vary based on key type - UUID fields shown in examples, but same hiding principle applies to business key fields
- `SiblingOrderNumber` - Keep visible (do not hide) as it's useful for users to see the ordering
