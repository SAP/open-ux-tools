# ABAP RAP Treeviews - Complete Introduction

This document consolidates key information about treeviews in the ABAP RESTful Application Programming Model (RAP).

---

## 1. Treeviews Overview

### What are Treeviews?

Using RAP, you can use CDS hierarchies to model hierarchical structures and expose them as treeviews to the SAP Fiori UI. A treeview visualizes data modeled by a CDS hierarchy using a SAP Fiori Elements treetable.

### Motivation and Business Context

Business data is often hierarchically structured in parent-child relationships, such as:

- **Company or department structures** with employees and their managers
- **Material and product classifications** (e.g., for customs)
- **Manufacturing products** with hierarchical structure (e.g., component parts of a car)

Such data is often visualized as a treeview - a collapsible SAP Fiori Elements treetable with a hierarchy of nodes. Each table entry serves as a hierarchy node, with the top entry as the hierarchy root node.

**Example:** An employee hierarchy where each employee can also be a manager (self-referencing hierarchy). The manager ID refers back to the employee ID of the manager.

### Technical Foundation

Treeviews in RAP are based on:

- **SAP HANA database** - Provides built-in functions for handling hierarchical data
- **ABAP CDS** - Provides means to query hierarchical data stored in database tables
- **CDS hierarchies** - Design-time entities for working with hierarchical data (reusable in other CDS entities and RAP business objects)

CDS hierarchies outside RAP are mainly used for analytical scenarios. With RAP, you can use CDS hierarchies to create **transactional, draft-enabled SAP Fiori apps** with a treeview.

## 2. Treeview Features

RAP supports both **read-only** and **editable treeviews** with advanced features.

### Available Features in Editable Treeviews

| Feature | Managed Implementation | Unmanaged Implementation | Notes |
|---------|----------------------|--------------------------|-------|
| **Reassign hierarchy node** (drag & drop or cut & paste) | Declare link and unlink actions | Declare and implement link and unlink actions | Allows moving child nodes to different parent nodes |
| **Move node among siblings** (reorder) | Declare managed reorder action OR implement custom | Declare and implement custom reorder action | Sibling order number determines display order. Managed reorder requires single field (integer/numc). For multiple fields or business semantics, use unmanaged. |
| **Copy hierarchy node** | Declare and implement custom copy action | Declare and implement custom copy action | No managed copy action available. Can be implemented recursively to copy child nodes too. |
| **Delete node with children** | Use `with cascading delete` syntax | Implement custom cascading delete | Optional but recommended - UI expects server to cascade deletion for subtrees |
| **Inline editing** | Provided by RAP framework | Provided by RAP framework | Available after implementing editable treeview (e.g., change employee names/data) |

### Important Notes on Features

**Reorder Action:**
- A newly created child node doesn't have a sibling order number by default
- Sibling order numbers are only calculated when the reorder action is performed
- When a node is assigned to another parent, there can be duplicate sibling numbers until reorder is performed
- Implement a determination to ensure sibling numbers are always unique and non-empty

**Cascading Delete:**
- Even though optional, the UI expects server cascading for subtrees
- Without cascade, the UI doesn't behave consistently (doesn't send requests for multi-selected subtree nodes)

## 3. Hierarchy Directories

### What are Hierarchy Directories?

A **hierarchy directory** is a CDS view entity designed to provide a list ("directory") of multiple subhierarchies. It contains a field for distinguishing between all available alternative subhierarchies.

**Example:** A directory of travel agencies with their HR hierarchies, where the agency ID distinguishes between subhierarchies. Each agency has its own employee hierarchy.

### Hierarchy Directories and Editable Treeviews

**Critical Requirement:** For editable treeviews, hierarchies with directories are the **only** technically possible implementation.

- **Without a directory:** You only get a read-only treeview whose tree nodes can be edited on their object pages, but none of the features to change the tree itself (no drag and drop, etc.)

- **Directory filter requirement:** For editable treeviews, the directory filter of the CDS hierarchy must filter precisely on the composition-to-parent association of the hierarchy node

**Example Behavior:** 
- Directory filter works on the level of agency instances
- Hierarchies shown in the treeview always contain only employees from one selected single agency instance
- Employees from multiple agency instances are never mixed in one treeview

## 4. Architecture Overview

### Read-Only Treeview Architecture

The following artifacts work together:

1. **Database table** - For hierarchy data
2. **Interface view** - CDS view entity referring to database table, adds hierarchy node as self-projection
3. **CDS hierarchy** - Persistent CDS entity (defined using `DEFINE HIERARCHY`), adds hierarchical interpretation to the data
4. **Projection view** - Combines interface view information with hierarchical interpretation from CDS hierarchy
5. **Service definition & binding** - Expose the data and hierarchy to the UI

### Editable Treeview with Draft Architecture

The following artifacts work together:

1. **Active and draft database tables** - For hierarchical data and hierarchy directory

2. **Interface views** - CDS view entities referring to underlying database tables
   - Provide first projection layer
   - CDS view entities for hierarchy directory and hierarchical data are related using one-to-many association
   - Hierarchical data view includes self-association to parent node (adds hierarchy logic)

3. **CDS hierarchy** - Persistent CDS entity (defined using `DEFINE HIERARCHY`), adds hierarchical interpretation

4. **Base CDS views** - Select data from interface views and enrich with compositional information
   - Base CDS view for hierarchy directory: root view entity (composition parent)
   - Base CDS view for hierarchical data: composition child

5. **Behavior definition** - Defines transactional behavior
   - Adds draft capability
   - Adds editing functions for UI (link, unlink, reorder, copy actions)

6. **Projection views** - Interact with consumption layer
   - Directory projection: needed for exposure as transactional query
   - Hierarchical data projection: combines interface view information with hierarchical interpretation using `@OData.hierarchy.recursiveHierarchy` annotation

7. **Projection behavior definition** - Defines behavior of projection views

8. **Behavior implementation** - Implements additional features (authorizations, numbering, determinations, validations, etc.)

9. **Service definition & binding** - Expose the data and hierarchy to the UI

## Key Architectural Differences

| Aspect | Read-Only Treeview | Editable Treeview with Draft |
|--------|-------------------|------------------------------|
| Database tables | 1 active table | Active + draft tables (for data and directory) |
| Directory | Optional | **Required** |
| Composition | Not required | Required (parent-child relationship) |
| Behavior definition | Not required | Required (with draft and actions) |
| Associations | Self-projection | Self-association + parent association |
| Complexity | Lower | Higher (full transactional capability) |
